# Google indexing and owner release checklist

13 October 2026. No Google property, DNS record, hosting rule, campaign or production deployment was changed in this task.

## 1. Resolve release prerequisites

1. In the hosting project's domain settings, make `vedagroup.uk` the directly served production domain. Remove the existing apex-to-www redirect. Preserve HTTPS enforcement. Configure www to redirect permanently to https://vedagroup.uk, preserving path/query. Prefer a single edge redirect for HTTP/www variants. Do not redirect any unrelated Veda domain.
2. If the application handles www canonicalization instead, set `SEO_CANONICAL_REDIRECT=true` only after removing the opposite host rule. It is disabled by default to avoid a loop. Build-time configuration requires rebuilding. Verify `/about?source=check` and slash variants on both hosts after release.
3. Production build settings: `SITE_URL=https://vedagroup.uk` and production NODE_ENV (indexing is on by default; no SEO_INDEXING needed); on Vercel, Production environment only. Staging/preview: `SEO_INDEXING=false` plus host access protection. Vercel preview remains nonindexable even if the flag is accidentally true. Do not reuse a production artifact as a protected preview: static metadata/config is build-dependent.
4. Rotate the active exposed Resend key using its provider account. Create a replacement scoped to sending from the approved verified domain; securely update local/hosting server-only settings. Coordinate replacement/redeploy/revocation to minimize interruption, revoke the old key promptly, then check sender/admin/confirmation inboxes and provider events with one approved sample enquiry. Do not put either key in Git, chat or a report. Audit other exports and provider usage. Current local key was accepted for read access; rotation is outstanding.
5. Confirm `ENQUIRY_MODE=email`, verified `ENQUIRY_FROM`, approved `ENQUIRY_TO`, new `RESEND_API_KEY`, `SITE_ORIGIN=https://vedagroup.uk`, and both shared Upstash REST settings. Confirm the proxy overwrites `X-Real-IP`. Local .env has no origin/shared limiter configured; hosting state is unknown. Production handler intentionally fails closed when required settings are missing.
6. Approve actual privacy/processing disclosures, legal/trading identity, public contact details and existing client-logo usage. Current privacy page is a local-testing draft and is not sufficient disclosure for email collection. Keep Insights nonindexed until genuine approved articles exist.

## 2. Domain-property DNS verification

1. Sign in to the owner's Google account at [Search Console](https://search.google.com/search-console).
2. Open the property selector, choose Add property, select **Domain**, enter `vedagroup.uk` (no scheme, www, slash or path), and continue.
3. Copy the exact TXT value generated by Google: `google-site-verification=ACCOUNT_SPECIFIC_TOKEN`. The token cannot be invented or obtained from this repository.
4. In the authoritative DNS provider for vedagroup.uk, add a TXT record at the zone apex (`@`, blank or `vedagroup.uk` as required by that provider), with Google's exact value and the provider's normal TTL. Preserve existing TXT/MX/A/AAAA/CNAME records. This is an owner action, not performed here.
5. Check propagation using PowerShell: `Resolve-DnsName -Name vedagroup.uk -Type TXT`. Confirm the entire Google TXT value is returned, then click Verify in Search Console. If still pending, allow propagation and retry verification. Retain the record after verification.

Google's [ownership verification instructions](https://support.google.com/webmasters/answer/9008080) explain supported methods. The existing optional `GOOGLE_SITE_VERIFICATION` environment variable emits an HTML token for a **URL-prefix** property; it does not verify a Domain property. For that alternative, add `https://vedagroup.uk/`, choose HTML tag, configure only the tag's content token, rebuild/deploy, and verify. A Domain property is preferred because it covers protocol/host variants.

## 3. Public verification and sitemap submission

1. Check https://vedagroup.uk/ returns 200 directly; www and HTTP resolve to it without loops. Confirm one non-www canonical on homepage and representative services and no host `X-Robots-Tag: noindex`.
2. Open https://vedagroup.uk/robots.txt: expected public Allow `/`, API Disallow `/api/`, sitemap line https://vedagroup.uk/sitemap.xml. Do not block public CSS, JS, images or fonts.
3. Open https://vedagroup.uk/sitemap.xml: 16 distinct approved canonical routes; no Insights, legal drafts, 404s or fabricated lastmod dates. Sitemap discovery does not guarantee indexing. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
4. In Search Console, select the verified property, open **Sitemaps**, enter `https://vedagroup.uk/sitemap.xml`, submit once and record fetch status and discovery date. Investigate fetch errors rather than repeatedly resubmitting.

## 4. URL Inspection and structured data

Inspect `/`, `/about`, `/services`, `/contact`, `/services/international-market-entry` and `/services/export-business-development`. Record indexed/not indexed status and reason, last crawl, crawl permission, fetch/render result, user-declared canonical and Google-selected canonical. Use **Test live URL** and inspect rendered HTML/screenshot, especially service links and mobile content. Request indexing once for important changed URLs if eligible; requests require owner/full-user access and are not ranking boosts. [Recrawl guidance](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl).

Run [Rich Results Test](https://search.google.com/test/rich-results) for homepage, About and market-entry URL. Run [Schema Markup Validator](https://validator.schema.org/) for Organization/WebSite/WebPage/Service and breadcrumbs. Organization uses real name/domain/description and stable IDs; add phone/address/logo/sameAs only when verified and visible. Generic Service and WebSite markup need not produce a rich result; the Google test does not support site-name validation. Local JSON-LD syntax/reference checks passed; external tools have not validated the undeployed changes. [Organization guidance](https://developers.google.com/search/docs/appearance/structured-data/organization), [site names](https://developers.google.com/search/docs/appearance/site-names).

Review Page indexing, Crawl Stats, Security Issues and Manual Actions. Check CDN logs for authenticated Google crawler traffic and restrictions. A spoofed Googlebot user agent returning 200 does not prove access by actual Google IPs. Keep drafts crawlable on production so page-level noindex can be read. Private staging should be authenticated; robots/noindex alone does not make it private. [Google indexing requirements](https://developers.google.com/search/docs/essentials/technical).

## 5. Baseline, Core Web Vitals and Ads

Export Search Console Performance data by query/page/country/device: clicks, impressions, CTR and average position for the available initial period. Separate branded variations from service queries, including unresolved Space ambiguity without conflating entities. Record qualified enquiries in the owner's existing workflow; do not introduce unapproved tracking or retain personal data in SEO reports. Compare later equivalent periods and annotate launch dates.

Run mobile/desktop PageSpeed Insights and record lab versus CrUX field results and sample availability. Search Console Core Web Vitals and field p75 targets: LCP <=2.5s, INP <=200ms, CLS <=0.1. Local lab measurements are not field INP. [Measurement guidance](https://web.dev/articles/vitals-measurement-getting-started).

For any later Ads launch, separately verify AdsBot access, destination/device/country availability, final/display URL consistency, useful service content and approved identity/privacy/enquiry functionality. No ad setup, spend or approval is included in this work. [Destination requirements](https://support.google.com/adspolicy/answer/6368661?hl=en).
